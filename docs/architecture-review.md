### 3.1 A* Search (Module 3)

#### Finding F-ASTAR-1 - Heuristic admissibility proof is incorrect
**Severity: HIGH**

**Location:** `docs/architecture.md` Section 6.8 (lines 1038-1068)

**Problem:**
The architecture defines the heuristic as:

```python
def h(state) -> float:
    remaining = goal_required_skills - state
    if not remaining:
        return 0.0
    return sum(min_learning_cost(skill) for skill in remaining)
```

and claims admissibility because "it never overestimates (actual cost may be
higher due to prerequisites)."

The claim that `h` "never overestimates" is **only true if the cost of
learning a skill's prerequisites is NOT counted in the actual cost `g`**.
But the architecture's successor function (Section 6.6) explicitly requires
prerequisites to be learned first, and the cost function `g` (Section 6.7)
accumulates the cost of *every skill learned on the path*, including
prerequisites.

Consider: the role requires `Docker` (cost 15). `Docker` requires `Linux`
(cost 10) and `Networking` (cost 8). The heuristic at a state missing only
`Docker` returns `h = 15` (the cost of Docker alone). But the actual cost to
reach the goal from that state is `15 (Docker) + 10 (Linux) + 8 (Networking)
= 33`, because the prerequisites must also be learned.

In this direction, `h = 15 <= 33`, so `h` does not overestimate - admissibility
holds. **However**, the architecture's proof text is wrong in the opposite
direction: it says "actual cost may be higher due to prerequisites," which is
correct, but the proof does not address the case where a *missing required
skill's prerequisites are themselves required skills already counted in
`remaining`*. If `Linux` is also a required skill and is in `remaining`, then
`h` sums `15 (Docker) + 10 (Linux) = 25`, but the actual cost is `15 + 10 + 8
(Networking, a non-required prereq) = 33`. Still admissible.

The real admissibility risk is **double-counting**: if a prerequisite skill
appears both as a required skill (in `remaining`) and as a prerequisite of
another required skill, the heuristic sums its cost once (correct), but the
proof does not articulate why this is safe. More critically, the heuristic
does **not** account for the cost of non-required prerequisite skills at all,
which is fine for admissibility (underestimate) but means `h` can be a very
loose lower bound, making A* behave closer to Dijkstra and reducing the
heuristic's pruning benefit.

**Why it matters:**
The architecture repeatedly claims "A* guarantees this is the optimal
ordering" (Section 6.13, line 1214) and "optimal path guaranteed with
admissible heuristic" (Section 16.3, line 3051). If the heuristic were
inadmissible, the optimality guarantee would be void - a serious academic
defensibility problem. The heuristic as written *is* admissible, but the
proof is poorly reasoned and could mislead implementers into "improving" the
heuristic (e.g., adding prerequisite costs) in a way that breaks
admissibility.

**Recommended correction:**
- Rewrite the admissibility argument to state explicitly: `h(state)` sums
  the base learning cost of each missing *required* skill. The actual cost
  to reach the goal is at least this sum (because each required skill must be
  learned at least once at its base cost), and may be higher (due to
  non-required prerequisites). Therefore `h(state) <= h*(state)` and the
  heuristic is admissible.
- Add an explicit note: "Do NOT add prerequisite costs to `h`, as this would
  risk double-counting and could make `h` inadmissible."
- Acknowledge that `h` is a relaxed lower bound (it ignores prerequisite
  chains), so optimality is preserved but pruning may be limited. This is an
  acceptable trade-off for a small skill graph.

#### Finding F-ASTAR-2 - Cost function g(n) defined inconsistently
**Severity: MEDIUM**

**Location:** `docs/architecture.md` Section 6.7 (lines 1021-1036) and
Section 6.10 (lines 1083-1138)

**Problem:**
`g(n)` is defined in Section 6.7 as:

```python
def g(state) -> float:
    return sum(learning_cost(skill) for skill in (state - start_state))
```

This computes `g` from the *state* (set difference), not from the *path*. But
in the A* implementation (Section 6.10), `g` is tracked incrementally via
`came_from`:

```python
tentative_g = came_from[current_state][0] + cost
```

These two definitions agree **only if every skill in `state - start_state`
was learned exactly once on the path**. In a DAG where each skill is learned
at most once (enforced by the successor function requiring `X not in S`),
this holds. However, the architecture does not state this invariant
explicitly, and the two definitions could diverge if an implementer allows
re-learning or proficiency upgrades (the spec's roadmap output includes
`current_proficiency` and `target_proficiency`, implying proficiency
*upgrades* are possible - see Finding F-ASTAR-4).

**Why it matters:**
An implementer following Section 6.7's formula literally would recompute `g`
from the state on every node expansion, which is correct but inefficient. An
implementer following Section 6.10's incremental approach relies on the
"learned at most once" invariant. If the invariant is violated (e.g., by
supporting proficiency upgrades), `g` becomes inconsistent and A* may
produce non-optimal paths.

**Recommended correction:**
- State explicitly: "Each skill is acquired at most once per path; the
  successor function enforces `X not in S`. Therefore `g(state) = sum of
  learning costs of skills in (state - start_state)`, and the incremental
  `came_from` tracking is equivalent."
- If proficiency upgrades are in scope (see F-ASTAR-4), redefine the state
  to include proficiency levels, not just skill IDs.

#### Finding F-ASTAR-3 - "Optimal path" claim is overstated for the roadmap use case
**Severity: MEDIUM**

**Location:** `docs/architecture.md` Section 6.13 (line 1214), Section 16.3
(line 3051)

**Problem:**
The architecture claims A* "guarantees this is the optimal ordering given the
cost model and dependencies" (line 1214) and "optimal path guaranteed with
admissible heuristic" (line 3051).

A* finds the minimum-*cost* path, where cost = sum of learning hours. But the
roadmap's *educational value* is not solely a function of total hours. The
architecture's cost model is a single scalar (learning hours per skill), with
no edge costs for dependency relationships (Section 6.2 defines
`SkillEdge.edge_cost` but Section 6.6's successor function uses only
`learning_cost(X)`, ignoring `edge_cost`).

**Why it matters:**
Calling the result "optimal" in an academic viva could invite the question
"optimal with respect to what?" The answer is "minimum total learning hours
subject to prerequisite constraints," which is a legitimate but narrow
optimality. The `edge_cost` field is defined but unused, suggesting the
cost model was intended to be richer.

**Recommended correction:**
- Qualify the optimality claim: "A* finds the minimum-total-learning-cost
  path subject to prerequisite ordering constraints, given the configured
  cost model."
- Either use `edge_cost` in the successor function's cost computation, or
  remove the `edge_cost` field from `SkillEdge` to avoid implying unused
  functionality.

#### Finding F-ASTAR-4 - State representation ignores proficiency levels
**Severity: MEDIUM**

**Location:** `docs/architecture.md` Section 6.3 (lines 952-971), Section
6.12 (lines 1161-1180)

**Problem:**
The A* state is `frozenset of skill_ids` - a binary "known / not known"
representation. But the spec's roadmap output (Section 6.12) includes
`current_proficiency` and `target_proficiency`, and Module 2's gap report
distinguishes "weak" (has skill, below required level) from "missing"
(doesn't have skill).

A student who "knows Python at beginner" but needs "Python at advanced" has a
gap that the binary-state A* cannot represent. The goal test (Section 6.5)
checks only `required_skill in state` - set membership - not proficiency
level.

**Why it matters:**
This means A* only plans for *missing* skills, not *weak* skills. A student
weak in a required skill would receive a roadmap that ignores the needed
proficiency upgrade. Section 6.14 says the goal is built from
`missing_skills and weak_skills skill IDs`, but if a weak skill's ID is
already in the start state (because the student has it at beginner), the
goal test `required_skill in state` passes immediately and the upgrade is
never planned.

**Recommended correction:**
Choose one of:
- **Option A (simpler, recommended for 4-week scope):** Keep binary states.
  The roadmap only plans *missing* skills. Weak skills are addressed by
  Module 4's readiness scoring (proficiency facts), not by the roadmap.
  Document this limitation explicitly.
- **Option B (richer, more work):** State = `frozenset of (skill_id,
  proficiency_level)` tuples. Successor function includes "upgrade
  proficiency" transitions. Goal test checks proficiency >= required. This
  is more academically complete but increases state-space size and
  implementation effort.

Given the 4-week timeline, Option A with explicit documentation is
recommended, but the architecture must state this design choice clearly
rather than implying weak skills are planned via A*.

#### Finding F-ASTAR-5 - Worked example has an f(n) computation error
**Severity: LOW**

**Location:** `docs/architecture.md` Section 6.13 (lines 1188-1212)

**Problem:**
The worked example shows:

```
Step 1: Learn SQL (cost: 20h)
  f = 0 + 20 = 20
```

But `f = g + h`. After learning SQL, `g = 20` and `h` should be the sum of
remaining required skills' costs (REST APIs 15 + Linux 10 + Docker 15 +
System Design 25 = 65), so `f = 20 + 65 = 85`, not `20`. The example appears
to show only `g` (or only the incremental cost), mislabeling it as `f`.

**Why it matters:**
In a viva, an examiner asking "show me how f(n) is computed at each step"
would find this example incorrect. It undermines the academic defensibility of
the A* explanation.

**Recommended correction:**
Rewrite the worked example to show `g`, `h`, and `f` separately at each
step, e.g.:

```
Step 1: Learn SQL (cost 20h)
  g = 20, h = 15+10+15+25 = 65, f = 85
Step 2: Learn REST APIs (cost 15h)
  g = 35, h = 10+15+25 = 50, f = 85
...
```

### 3.2 Forward Chaining (Module 4)

#### Finding F-FC-1 - Dual classification mechanism creates contradictions
**Severity: HIGH**

**Location:** `docs/architecture.md` Section 7.8 (lines 1610-1627), Section
7.10 (lines 1660-1677), Appendix B Q7 (lines 3439-3443)

**Problem:**
The architecture defines **two independent classification mechanisms**:

1. **Forward Chaining classification** (Section 7.8): rules fire and assert
   `readiness_classification` into working memory. This is the
   rule-based/reasoned classification.

2. **Score-threshold classification** (Section 7.10):
   ```python
   if score >= 80: classification = "Role Ready"
   elif score >= 60: classification = "Nearly Ready"
   else: classification = "Needs Improvement"
   ```

The architecture acknowledges they "should agree" but provides a precedence
rule: "If they disagree ... the Forward Chaining classification takes
precedence as the primary classification, and the score is included as
supporting evidence" (line 1673-1677).

This creates several problems:
- The score-threshold classification (Section 7.10) is **dead code** if FC
  always takes precedence. Why compute it?
- If the score says "Role Ready" (85) but FC says "Needs Improvement" (because
  a rule condition failed), the user sees "Needs Improvement" with a score of
  85 - confusing and hard to explain.
- The spec (Section 6) defines classification by score ranges (80-100, 60-79,
  0-59), implying the score *is* the classification. The architecture
  deviates from this by making FC authoritative.

**Why it matters:**
This is the single most confusing part of the architecture. It creates two
sources of truth for classification, undermines the explainability goal
("why did the student get this classification?" - which one?), and
partially contradicts the spec's score-range definition. In a viva, an
examiner would likely ask "which classification is the real one?" and the
answer "FC wins but we also compute the other" is awkward.

**Recommended correction:**
Unify the two mechanisms. Recommended approach:

- **Make Forward Chaining the sole classification mechanism.** The rules
  assert the classification. The score is a *separate numeric summary* shown
  alongside, not a second classifier.
- **Remove the score-threshold if/else classification** (Section 7.10). The
  score is computed and displayed, but classification comes only from FC
  rules.
- **Align the rule thresholds with the spec's score ranges** so that the
  rules and the score *happen* to agree in normal cases, but the rule is
  authoritative. Document this clearly.
- Alternatively, if the spec's score-range classification must be honored,
  make the *score* authoritative and use FC only to *explain* the score. But
  this weakens FC's role as the "required algorithm."

The first option (FC authoritative, score is supporting evidence) is
recommended and consistent with the architecture's stated intent.

#### Finding F-FC-2 - `contributes_to_score` field is defined but never used
**Severity: HIGH**

**Location:** `docs/architecture.md` Section 7.3 (line 1355), Section 7.4
(lines 1366-1414), Section 7.9 (lines 1634-1656)

**Problem:**
Each rule's `Conclusion` has a `contributes_to_score: float` field (line
1355). The example rules assign values: `30` for role_ready, `20` for
nearly_ready, `0` for needs_improvement (lines 1381, 1396, 1408).

The Forward Chaining process diagram (Section 7.6, line 1547) says:
"Score: 60 + 20 = 80 (from rule contributions)" - implying the score is the
sum of `contributes_to_score` values from fired rules.

But the actual scoring function (Section 7.9, `compute_readiness_score`) is a
**weighted factor formula** that does NOT use `contributes_to_score` at all:

```python
score = (
    weights["skill_coverage"] * facts["skill_coverage_percent"] +
    weights["core_skill_coverage"] * facts["core_skill_coverage_percent"] +
    ...
)
```

So there are **two scoring models** in the same document:
- Model A (implied by `contributes_to_score` and Section 7.6): score = sum of
  fired rules' `contributes_to_score`.
- Model B (Section 7.9's `compute_readiness_score`): score = weighted sum of
  factor percentages.

These produce different numbers. Section 7.6's example score of 80 (from
60+20) would not match Section 7.9's formula output for the same facts.

**Why it matters:**
This is an internal inconsistency that will manifest as a bug: depending on
which scoring path an implementer follows, the student gets a different
score. It also muddies the academic story - is the score rule-derived (FC)
or formula-derived (deterministic)? The spec (Section 13) says the score
must be "derived from measurable factors," which supports Model B, but then
`contributes_to_score` is misleading dead data.

**Recommended correction:**
Pick one scoring model and remove the other:
- **Recommended:** Keep Model B (weighted factor formula, Section 7.9) as
  the score computation, since it satisfies the spec's "measurable factors"
  requirement and is explainable. **Remove `contributes_to_score`** from
  the rule schema and fix Section 7.6's diagram to show the score computed by
  the formula, not by summing rule contributions.
- **Alternative:** If rules should drive the score, replace
  `compute_readiness_score` with a function that sums `contributes_to_score`
  from fired rules. But this makes the score less tied to measurable factors
  and harder to justify per the spec.

#### Finding F-FC-3 - Forward Chaining rule chaining is limited
**Severity: MEDIUM**

**Location:** `docs/architecture.md` Section 7.5 (lines 1425-1508)

**Problem:**
The Forward Chaining engine has these characteristics:
- Each rule fires **at most once** (`fired_ids` set, line 1449).
- Per iteration, it selects **one** highest-priority applicable rule and fires
  it (line 1464).
- The example rules (Section 7.4) all conclude the *same* fact key
  (`readiness_classification`), so once one fires, the others' conditions may
  still be met but they would overwrite the classification.

The architecture's test strategy (Section 13.3) includes `test_rule_chain`
("Rule A's conclusion enables Rule B. Verify both fire in order"). But the
example rule base has **no rules where one rule's conclusion enables
another** - all three rules conclude `readiness_classification` and none
conclude a fact that another rule's condition depends on.

A genuine Forward Chaining demonstration benefits from at least one
multi-step chain where an intermediate rule asserts a fact (e.g.,
`core_skills_satisfied = true`) that enables a downstream rule (e.g.,
`role_ready`). Without this, the engine is technically correct but
demonstrates only single-step inference, which an examiner could view as
"glorified if/else."

**Why it matters:**
The AGENTS.md (Section 12) warns against "renaming ordinary rule checks as
Forward Chaining." A rule base where only one classification rule ever fires
per run, with no chaining, is close to that line. The engine *supports*
chaining, but the configured rules don't *exercise* it.

**Recommended correction:**
- Add intermediate rules to the example rule base that create a genuine
  inference chain. For example:
  - Rule: IF `core_skill_coverage_percent >= 90` AND `min_core_proficiency
    >= 2` THEN `core_skills_satisfied = true` (priority 90)
  - Rule: IF `core_skills_satisfied == true` AND `skill_coverage_percent >=
    80` AND `learning_progress_percent >= 70` THEN
    `readiness_classification = role_ready` (priority 100)
  - This makes the `role_ready` rule depend on a fact *derived by inference*,
    not just on raw input facts - a genuine forward chain.
- Ensure the `test_rule_chain` test has a rule base that actually chains.

#### Finding F-FC-4 - Default rule with empty conditions fires unconditionally
**Severity: LOW**

**Location:** `docs/architecture.md` Section 7.4 (lines 1401-1419)

**Problem:**
`rule_needs_improvement_default` has `conditions: []` (empty list). The
`_conditions_met` method (line 1477) returns `True` for an empty condition
list (the loop body never executes, so no `return False` is hit). This means
the default rule is *always* applicable.

Because the engine fires the highest-priority applicable rule first and marks
rules as fired, the default rule (priority 10) will only fire after the
higher-priority classification rules have either fired or been found
inapplicable. This is correct behavior, but it relies on the priority ordering
and the "fire at most once" invariant.

**Why it matters:**
This is correct but subtle. If an implementer changes the engine to fire
*all* applicable rules per iteration (a common FC variant), the default rule
would fire alongside a higher classification, overwriting it. The
architecture should note this dependency explicitly.

**Recommended correction:**
- Add a comment in the rule base: "The default rule has empty conditions and
  is always applicable. It must have the *lowest* priority so it only fires
  when no other classification rule fires. Do not change the engine to
  fire-all-applicable without also changing this rule's semantics."

### 3.8 Academic Defensibility

#### Finding F-ACAD-1 - A* and Forward Chaining are genuinely designed
**Severity: INFO (positive confirmation)**

**Observation:**
- **A* (Module 3):** The design includes graph representation (DAG),
  state-space nodes (frozensets), successor function with prerequisite
  enforcement, cost function `g`, heuristic `h`, `f = g + h`, open list
  (min-heap), closed list (set), path reconstruction via `came_from`. This
  is a genuine A* formulation, not a disguised topological sort. The
  state-space approach (vs. searching over individual skills) is the correct
  way to model skill acquisition as a search problem.
- **Forward Chaining (Module 4):** The design includes facts (key-value),
  rules (IF-THEN with conditions), working memory (dict), rule matching
  (`_conditions_met`), rule firing (`_fire_rule`), an inference loop
  (`while True` with termination when no rule fires), and an inference
  trace. This is a genuine forward-chaining inference engine, not disguised
  if/else.

Both algorithms are placed in pure-Python packages (`modules/.../astar/`,
`modules/.../forward-chaining/`) separate from application orchestration,
enabling isolated testing without DB/HTTP. This is academically defensible.

**Caveats (covered by other findings):**
- The A* heuristic admissibility proof needs correction (F-ASTAR-1).
- The Forward Chaining rule base should include a genuine multi-step chain
  (F-FC-3).
- The dual classification mechanism must be resolved (F-FC-1, F-FC-2).
- The worked example's `f(n)` computation is wrong (F-ASTAR-5).

Once these are corrected, both algorithms are defensible in a viva.

## 6. Architecture Verdict

```
ARCHITECTURE VERDICT: APPROVE WITH CHANGES
```

### Justification

The architecture is **fundamentally sound, scope-appropriate, and
academically defensible in its core design**. The architect has:

- Correctly locked the four-module structure and linear dependency flow.
- Designed genuine A* and Forward Chaining implementations with the correct
  conceptual components, placed in pure-Python packages for isolated
  testing.
- Chosen a proportional technology stack (React + FastAPI + SQLite + spaCy +
  RapidFuzz) with no enterprise over-engineering.
- Correctly excluded the AI Role-Specific Assessment feature.
- Established a clear AI/NLP boundary that protects the required algorithms.
- Documented decisions with evidence, alternatives, and trade-offs.

However, **three HIGH-severity issues must be resolved before
implementation**:

1. The A* heuristic admissibility proof is incorrect and could mislead
   implementers into breaking optimality (F-ASTAR-1).
2. The dual readiness classification mechanism (FC vs score thresholds)
   creates contradictions and undermines the role of Forward Chaining
   (F-FC-1).
3. The `contributes_to_score` field implies a rule-driven score that the
   scoring formula ignores, creating two inconsistent scoring models
   (F-FC-2).

These are **correctable within the architecture document without
rearchitecting the system**. None of them require changing the technology
stack, module structure, or algorithm placement. They are documentation and
design-consistency fixes.

Once the HIGH-severity issues (and ideally the MEDIUM-severity issues,
particularly F-ASTAR-4/F-MOD-2 on weak-skill planning and F-DB-2 on the
missing Project entity) are resolved, the architecture will be ready to
support implementation.

The reviewer recommends that the architect revise `docs/architecture.md` to
address the HIGH and MEDIUM findings, then submit for a follow-up review
before Week 1 implementation begins.
